30 project questions

01 / The project

01What does your project do in one minute?›

It lets 5–10 human players play Secret Hitler in person or online without physical cards. Each player uses their own device to see their role, vote, handle policies, and follow the board. The server controls the game state, so players cannot decide their own role or reveal someone else’s private information.

Point to: docs/spec.md §1–3 and the live game.
02Can you walk me through a complete user journey?›

A player signs up or logs in, chooses a username, and creates or joins a room with its code and password. When 5–10 players are ready, the host starts the game. The app reveals each private role, moves through nomination, voting, legislation and powers, then shows the winner and saves a game-history entry.

Point to: docs/spec.md §3 and apps/mobile/app/.
03How are in-person and online modes different?›

Both modes use the same server rules and each player still needs a device and internet access. In-person players talk aloud and can arrange seats to match their physical table. Online mode provides table chat and normally uses timers; its seat order is shuffled at the start.

Point to: docs/spec.md §2.
04Is this already a native Android and iOS release?›

The Expo codebase targets Android, iOS, and the web, and the game is deployed as a web app. Distributable native store builds and broad device testing are still separate release work. I would demonstrate the live web version today rather than claim a published App Store or Play Store release.

Point to: README.md “Platforms and hosting”.

02 / Architecture

05Why did you divide the repository into apps and packages?›

The mobile/web app renders the interface, while the server handles accounts, rooms and live games. The engine package contains game rules, protocol contains shared event schemas, and theme contains design tokens and visible copy. This keeps the rules in one place instead of duplicating them in each client.

Point to: apps/mobile, apps/server, packages/engine, packages/protocol, packages/theme.
06Why is the server the source of truth?›

Social-deduction games rely on hidden information. A client sends an action such as “vote Yes” or “nominate this player”; it does not send the new game state. The server checks whether the action is legal, applies it with the engine, saves the result, and sends each player an appropriate view.

Point to: apps/server/src/game/gameService.ts.
07What does “pure game engine” mean here?›

The rules in packages/engine work with inputs and return new state without database calls, network calls, timers, or direct Math.random(). Randomness is passed in as a function. That makes the same rules deterministic in tests and usable by the server during real matches.

Point to: packages/engine/src/ and rule tests.
08Why are presidential powers stored as board data?›

The Fascist track differs by player count. Instead of hard-coding “slot two always investigates,” the engine reads the 5–6, 7–8, or 9–10 player board configuration. This prevents the wrong power from appearing when the same slot means something different at another table size.

Point to: docs/spec.md R5 and packages/engine/src/boards.ts.
09Why use REST and Socket.IO together?›

REST is suitable for requests such as creating a room, joining it, or loading history. Socket.IO handles live updates during the lobby and game, where all players must see the current state quickly. The client still receives only its own projected game view.

Point to: apps/server/src/app.ts, apps/server/src/realtime/.
10What if two players send game actions at almost the same time?›

The game service serializes actions by room. It processes one action against the latest saved state, then handles the next one. Each action is also checked for phase, actor and target, so a late duplicate vote is rejected rather than changing the tally twice.

Point to: createGameService in apps/server/src/game/gameService.ts.

03 / Trust and private information

11How do you stop one player from seeing another player’s role or policy hand?›

The full state remains on the server. Before sending an update, projectView(state, playerId) builds a player-specific version. A phone gets its own role and any private result it is entitled to, while another player’s role, hand, discarded policies and unrevealed vote stay off that phone.

Point to: packages/engine/src/projectView.ts and leak tests.
12How does voting stay secret until reveal?›

The server records each vote privately. Other players can see who has already voted, but not Yes or No. Once all votes are in, the host confirms the reveal; the server tallies and broadcasts the result. A tie fails because the government needs more than half of the living players voting Yes.

Point to: docs/spec.md R17–R20 and §6.
13What do different roles know when the game begins?›

Liberals learn only their own role. At 5–6 players, Hitler and the other Fascist know each other. At 7–10 players, Fascists know their teammates and Hitler, while Hitler knows nobody. The server constructs these different private views instead of sending one role list to all players.

Point to: docs/spec.md R8–R10 and packages/engine/src/knowledge.ts.
14How does email login work, and what does the server verify?›

Firebase Authentication handles email/password sign-up and sign-in. The client includes a Firebase ID token with protected requests and socket connections. The server verifies the token’s signature and claims before associating the action with a user; the server does not trust a username supplied as an identity claim by the client.

Point to: apps/mobile/src/lib/firebase.ts and apps/server/src/auth/tokenVerifier.ts.
15Why is a room password not saved as plain text?›

The server hashes it with Argon2 and checks a joining player’s submitted password against the hash. A database record or room response therefore does not need to expose the original password. I also check that room views do not leak the stored hash.

Point to: apps/server/src/rooms/roomService.ts and room tests.
16Why do Liberal and Fascist role cards have the same layout?›

Presentation must not reveal hidden information by accident. The card keeps the same size, position, motion and structure across roles. Hitler’s card has “Fascist” as the large party heading and “Hitler” in smaller type below; an investigation reveals only the party, so Hitler appears as Fascist there.

Point to: apps/mobile/src/components/RoleCard.tsx and docs/spec.md R3/R38.

04 / Rules and edge cases

17What happens after three failed elections?›

Chaos enacts the top policy of the deck without triggering that board slot’s presidential power. The election tracker returns to zero and term limits are cleared. The enacted policy can still unlock veto or win the game, so the engine checks those outcomes.

Point to: docs/spec.md R21–R24 and packages/engine/src/chaos.ts.
18When does electing Hitler as Chancellor end the game?›

Once at least three Fascist policies have been enacted, a successful election with Hitler as Chancellor gives the Fascists an immediate win. Before that threshold, electing Hitler does not end the game. If the elected Chancellor is someone else, the game shows a public “Not Hitler” badge.

Point to: docs/spec.md R25/R46.
19What exactly does an investigation tell the President?›

Only the target’s party membership, not their exact role. Hitler belongs to the Fascist party, so an investigation of Hitler says “Fascist,” not “Hitler.” The President sees that result privately, while the table only sees who was investigated.

Point to: docs/spec.md R3/R38 and packages/engine/src/projectView.ts.
20What changes after a Special Election?›

The current President picks another living player to be President for one round. After that round, the ordinary clockwise order resumes from the player after the President who called the power, not from the temporary President. This is an easy edge case to get wrong, so it has specific tests.

Point to: docs/spec.md R12/R39 and packages/engine/src/seating.ts.
21When can a government veto its policy choice?›

Veto becomes available after the fifth Fascist policy, regardless of whether a government or Chaos enacted it. The Chancellor requests it and the President decides. An agreed veto discards both policies and advances the failed-election tracker; a refusal forces the Chancellor to enact one of the two.

Point to: docs/spec.md R33–R35 and packages/engine/src/veto.ts.
22Why does the number of players affect roles and powers?›

Secret Hitler changes its role distribution and Fascist board by table size. For example, five players get three Liberals, one ordinary Fascist and Hitler; ten players get six Liberals, three ordinary Fascists and Hitler. The engine chooses both the role counts and power track from the configured player count.

Point to: docs/spec.md R1–R5.

05 / Reliability, testing and deployment

23What happens if the game server restarts in the middle of a match?›

Room data and live game snapshots are stored in PostgreSQL, so a restarted server can load them again. Turn timers are re-armed using the time remaining, instead of giving a fresh full timer. The client reconnects and receives its current projected view.

Point to: apps/server/src/rooms/roomStore.ts, apps/server/src/game/gameStore.ts, apps/server/src/game/gameService.ts.
24What data goes into PostgreSQL?›

Prisma models users, authentication methods, rooms and memberships, completed games, players and public game events. The deployment also persists active rooms and game snapshots in separate live-state tables. The Firebase account itself is handled by Firebase Authentication; the app’s username and game history are server data.

Point to: apps/server/prisma/schema.prisma.
25How do you validate messages before applying a game action?›

Shared Zod schemas check the action’s shape, such as the allowed vote names and policy tile indices. The server then uses the engine to check whether that action is legal for this player in this phase. Shape validation and game-rule validation solve different problems, and both are needed.

Point to: packages/protocol/src/game.ts and apps/server/src/realtime/sockets.ts.
26How did you test more than the happy path?›

Rules have named tests using IDs R1–R48. The simulator completed 10,000 legal games for each table size from 5 to 10, and separate tests checked 12,000 player views for secret leaks. Server socket tests also play complete games and a restart-recovery case.

Point to: packages/engine/src/*.test.ts, tools/sim/src/, apps/server/src/game/socketGames.test.ts.
27Was the deployed game tested with actual server requests?›

Yes. A production smoke test created five disposable authenticated players, created and joined a room, started a match, played through the real Socket.IO server to a winner, checked private views and saved history, then removed the test accounts. This complements local unit and integration tests, but it does not replace a larger human playtest.

Point to: tools/sim/src/liveFullGame.ts and the deployed game link above.
28Describe a real bug you found while testing and how you fixed it.›

Starting a room initially failed because the client labelled a request with no body as JSON. Fastify expected a JSON body and rejected the empty one. I changed the shared request helper to add the JSON content type only when a body exists, added a regression test, and then verified the room-start flow in a full deployed match.

Point to: apps/mobile/src/lib/api.ts and apps/mobile/src/lib/api.test.ts.
29Where is each deployed part hosted?›

The static web client and Node game server are deployed as separate Render services. The server connects to Neon PostgreSQL for durable data. Firebase Authentication handles email/password identities. This separation lets the static site load quickly while the server keeps the real-time game state.

Point to: README.md “Platforms and hosting” and the live game.
30What is unfinished, and what would you improve next?›

The live web game and the core multiplayer path have been tested, but I would not call every browser or native release verified. Next I would do real games with multiple friend groups, test Safari and low-end devices, complete accessibility and release checks, and package the Android/iOS binaries. Keeping those limits explicit is more honest than claiming every platform is production-ready.

Point to: docs/plan.md Steps 15–16 and README.md.
